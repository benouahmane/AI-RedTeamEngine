================================================================
 AI RED TEAM ENGINE — END-TO-END SETUP & RUN GUIDE (KALI LINUX)
================================================================

This file is the single source of truth for getting the engine
running on a fresh Kali Linux VM. Follow the sections in order.

----------------------------------------------------------------
 PREREQUISITES
----------------------------------------------------------------

  - Kali Linux VM (rolling release, 2024+).
  - At least 4 GB RAM and 30 GB free disk (GVM and the Docker
    images are the largest chunks).
  - Outbound internet access (only during install, not for the
    agent at runtime).
  - An Anthropic API key (sk-ant-...).
  - At least one isolated lab target the agent is allowed to
    touch. Defaults assume Metasploitable on 192.168.163.131.

----------------------------------------------------------------
 STEP 0 — PREPARE THE TARGET VM (DO THIS FIRST)
----------------------------------------------------------------

  Nothing below works until Kali can reach a target. Set this up
  before installing anything.

  1. In your hypervisor, put BOTH Kali and the target VM on the
     same isolated network:
       - VirtualBox:  Host-Only Adapter (vboxnet0)
       - VMware:      Host-only
       - KVM/libvirt: an isolated virtual network
     Host-Only / isolated keeps the deliberately vulnerable target
     off your real LAN and off the internet — required by section 9
     of the FYP brief.

  2. Boot the target and find its IP:
       ip a          (Linux target, e.g. Metasploitable)
       ipconfig      (Windows target)

  3. Give it a STATIC IP or a DHCP reservation. On plain DHCP the
     address can change after a reboot, and you will then either
     scan nothing or scan whichever device inherited the lease.

  4. Confirm reachability FROM KALI:

       ping -c3 192.168.163.131

     If this fails, fix networking before continuing — every later
     step depends on it.

  5. Note the IP. It must fall inside ALLOWED_TARGET_RANGES in
     STEP 3, or the agent will refuse every action.

----------------------------------------------------------------
 STEP 1 — CLONE THE REPO
----------------------------------------------------------------

    git clone https://github.com/benouahmane/AI-RedTeamEngine.git
    cd AI-RedTeamEngine

----------------------------------------------------------------
 STEP 2 — RUN THE SETUP SCRIPT
----------------------------------------------------------------

    chmod +x setup_kali.sh
    ./setup_kali.sh

  This installs:
    - OS tools: nmap, gobuster, ffuf, nikto, sqlmap, theharvester,
      metasploit-framework, hashcat, hydra, john, gvm, gvm-tools,
      crackmapexec (or netexec), nuclei, rustscan
    - Docker + docker-compose
    - Python venv (.venv/) and everything in requirements.txt
    - nodejs + npm (needed to build the CALDERA web UI)
    - CALDERA into ./caldera with its own venv, pinned to release
      5.3.0 from github.com/apache/caldera — a REQUIRED component
      (FYP brief 1.1 / 2.4). If this part fails, setup finishes the
      rest and prints a loud CALDERA INSTALL FAILED block at the
      end with retry commands. Do not ignore it.
    - Copies .env.example to .env if .env doesn't exist yet

  Takes 15-30 minutes. GVM (~1 GB), pip installs, and the CALDERA
  npm build are the slow parts. Type your sudo password when asked.

  If the script reports it added you to the 'docker' group, log
  out and back in (or run: newgrp docker) before continuing.

----------------------------------------------------------------
 STEP 3 — CONFIGURE SECRETS
----------------------------------------------------------------

    nano .env

  ONE setting has no working default and must be filled in — which
  one depends on LLM_PROVIDER:

    LLM_PROVIDER=anthropic     (default)
        ANTHROPIC_API_KEY=sk-ant-...your real key...

    LLM_PROVIDER=openrouter
        OPENROUTER_API_KEY=sk-or-...your real key...
        OPENROUTER_MODEL=anthropic/claude-sonnet-4.6

  The engine reads only the key for the provider you selected, so a
  blank ANTHROPIC_API_KEY is fine on openrouter and vice versa.

  ONE setting to check against your lab — it ships pre-filled with
  the three environments from the brief, so if your target from
  STEP 0 is on 192.168.163.0/24 it already works untouched:

    ALLOWED_TARGET_RANGES=192.168.163.0/24,10.10.0.0/16,10.20.0.0/16
        Comma-separated CIDR allowlist. The IP from STEP 0 MUST be
        inside one of these or every action is rejected as "out of
        scope". Add your CIDR if your lab uses different addressing.

        Keep the mask tight — the agent may touch anything inside
        the ranges listed here. If the target shares a LAN with
        real devices, pin the single host:
            ALLOWED_TARGET_RANGES=192.168.163.131/32

        Leaving it EMPTY disables the check entirely (everything is
        allowed). The CLI warns on stderr when this happens; never
        blank it out just to make an error go away.

  Everything else has working defaults that match this guide:

    LLM_PROVIDER             "anthropic" or "openrouter"
                             openrouter = one key, many vendors; set
                             OPENROUTER_API_KEY + OPENROUTER_MODEL.
                             Intended for cross-model benchmark runs —
                             see CHOOSING AN LLM PROVIDER below.
    ANTHROPIC_MODEL          default: claude-sonnet-4-6
    NEO4J_PASSWORD           must match docker-compose.yml
    CALDERA_API_KEY          must match the CALDERA server (STEP 6B)
    DEFAULT_MODE             "human_in_loop" or "autonomous"

  NOTE: .env is read ONCE when the Python process starts. After
  editing it, stop the running engine/dashboard and relaunch —
  starting a new session inside the same process will not pick up
  the change.

----------------------------------------------------------------
 CHOOSING AN LLM PROVIDER
----------------------------------------------------------------

  The engine supports two. Only the key and model differ — the
  agent itself is identical in both cases.

  anthropic   (default, recommended)
      ANTHROPIC_API_KEY=sk-ant-...
      ANTHROPIC_MODEL=claude-sonnet-4-6
      The orchestration stack named in the FYP brief (section 2.1).
      Prompt caching is handled automatically. Use this for the runs
      that produce your assessment reports.

  openrouter  (for benchmark comparisons)
      OPENROUTER_API_KEY=sk-or-...
      OPENROUTER_MODEL=qwen/qwen3.8-max
      One key, many vendors. Added so the same target can be re-run
      under a different model and scored, which is what turns D5 into
      a measured comparison instead of a citation.

  COST — roughly, for one complete Metasploitable 2 run (~60 steps):
      claude-sonnet-4-6   ~ $1.00
      qwen/qwen3.8-max    ~ $0.60
  Both rise to about $3.34 / $2.00 if a session runs to the
  MAX_AGENT_STEPS ceiling of 200. LLM cost is not a constraint on
  this project; reliability matters more than the price difference.

  The system prompt carries the ~35k-character tool catalogue and is
  re-sent every step, so whether prompt caching engages changes cost
  by roughly 2.5x — more than the choice of model does. Anthropic
  handles this automatically. On OpenRouter, run once, check the
  dashboard, and set OPENROUTER_CACHE_SYSTEM=true if cached tokens
  are not being billed at the cheaper rate.

  KEEP ONE MODEL PER BENCHMARK COMPARISON. Scoring one target with
  one model and another target with a different model compares the
  models, not the targets, and the numbers become meaningless.

----------------------------------------------------------------
 STEP 4 — START THE DATABASES (POSTGRES + NEO4J)
----------------------------------------------------------------

    docker compose up -d
    docker compose ps

  You should see both services healthy:
    - postgres   localhost:5432
    - neo4j      localhost:7474 (browser), localhost:7687 (Bolt)

  The Neo4j browser at http://localhost:7474 is handy for
  inspecting BloodHound data — login with neo4j / bloodhoundpass
  (or whatever you set NEO4J_PASSWORD to).

----------------------------------------------------------------
 STEP 5 — APPLY DATABASE MIGRATIONS
----------------------------------------------------------------

    source .venv/bin/activate
    alembic upgrade head

  This creates the tables the agent writes to:
    - pentest_sessions, task_nodes, hosts, vulnerabilities,
      credentials, agent_decisions

  From this point on, every shell where you run the engine must
  have the venv active. Re-run `source .venv/bin/activate` in
  each new terminal.

----------------------------------------------------------------
 STEP 6 — START THE METASPLOIT RPC DAEMON
----------------------------------------------------------------

  The metasploit wrapper talks to msfrpcd, which must be running.
  Two ways to start it:

  (a) One-shot in a terminal (good for first runs):

        ./scripts/start_msfrpc.sh

      Leave this terminal open; it stays in the foreground.

  (b) As a systemd service (auto-starts on boot):

        # Edit the unit file: replace REPLACE_WITH_YOUR_USER and
        # REPLACE_WITH_REPO_ABSPATH with the right values.
        nano scripts/msfrpcd.service

        sudo cp scripts/msfrpcd.service /etc/systemd/system/
        sudo systemctl daemon-reload
        sudo systemctl enable --now msfrpcd
        sudo systemctl status msfrpcd

  Verify it's listening:

      ss -tlnp | grep 55553

----------------------------------------------------------------
 STEP 6B — START THE CALDERA SERVER
----------------------------------------------------------------

  CALDERA drives the `caldera` simulation tool: MITRE ATT&CK-mapped
  adversary emulation and the purple-team telemetry consumed by the
  paired P2-BLUE project. It is a required component of this project
  (FYP brief section 1.1 Core Technologies and section 2.4 Tool
  Stack), not an optional add-on.

  setup_kali.sh already cloned + installed CALDERA into ./caldera,
  pinned to release 5.3.0 from https://github.com/apache/caldera
  (the project moved from mitre/ to apache/). It needs Python 3.10+,
  which Kali rolling already provides.

  Two ways to start it (mirrors the msfrpcd options above):

  (a) One-shot in a terminal:

        ./scripts/start_caldera.sh

      Leave it running in the foreground. The script regenerates
      caldera/conf/local.yml from .env on each start, so the red
      API key it serves always matches CALDERA_API_KEY in .env.

      The FIRST start is slow — it bundles the VueJS UI via npm.
      Later starts reuse the cached build; to skip the build step
      entirely once it exists: CALDERA_BUILD=0 ./scripts/start_caldera.sh

  (b) As a systemd service (auto-starts on boot):

        # Edit the unit: replace REPLACE_WITH_YOUR_USER and
        # REPLACE_WITH_REPO_ABSPATH.
        nano scripts/caldera.service

        sudo cp scripts/caldera.service /etc/systemd/system/
        sudo systemctl daemon-reload
        sudo systemctl enable --now caldera
        sudo systemctl status caldera

  Verify it's listening (default port 8888):

      ss -tlnp | grep 8888
      curl -s -H "KEY: $CALDERA_API_KEY" \
           http://127.0.0.1:8888/api/v2/adversaries | head

  Web UI: http://localhost:8888  — login red / admin

----------------------------------------------------------------
 STEP 6C — DEPLOY CALDERA AGENTS ONTO THE LAB TARGETS
----------------------------------------------------------------

  CALDERA does NOT exploit its way in. It only runs ability chains
  through its own agents (sandcat), so each lab target you want it
  to emulate against needs one installed. Until then the tool's
  list_agents returns empty and operations have nothing to run on.

  This is the one part of CALDERA that cannot be scripted from
  here — it runs ON the target, not on Kali.

  1. In the CALDERA UI, go to:  Agents -> Deploy an agent
  2. Pick "Sandcat" and the target's platform (linux / windows).
  3. Set the callback host to your KALI IP (not 127.0.0.1, or the
     agent will call back to itself and never appear).
  4. Copy the generated one-liner, run it ON the target VM.
  5. The agent should appear in the Agents table within ~60s.

  Reachability both ways matters: the target must reach Kali on
  port 8888 for agent check-in. If agents never appear, test from
  the target:  curl http://<KALI_IP>:8888

  Order of operations in a session: use the engine's own tools
  (nmap -> nuclei -> metasploit) to compromise a host first, then
  install the sandcat agent on it, then let the agent drive
  CALDERA in the objective phase for repeatable ATT&CK-mapped
  emulation and blue-team telemetry.

----------------------------------------------------------------
 STEP 7 — (OPTIONAL) SMOKE-TEST WITH PYTEST
----------------------------------------------------------------

    pytest -v

  All 129 tests should pass. They mock the offensive binaries, so
  failures here mean code/dependency problems, not lab issues.

----------------------------------------------------------------
 BEFORE STEP 8 — WHAT MUST BE RUNNING
----------------------------------------------------------------

  A live session needs these up at the same time. Every terminal
  that runs Python needs `source .venv/bin/activate` first.

    Terminal 1   docker compose up -d          Postgres + Neo4j
                 (detached — start once, stays up)
    Terminal 2   ./scripts/start_msfrpc.sh     Metasploit RPC
                 (foreground — required for exploitation)
    Terminal 3   ./scripts/start_caldera.sh    CALDERA server
                 (foreground — first start is slow)
    Terminal 4   your working shell            run the engine here

  Terminals 2 and 3 are unnecessary if you installed the systemd
  units in STEP 6 / 6B. Confirm the listeners either way:

      ss -tlnp | grep -E '55553|8888'

----------------------------------------------------------------
 STEP 8 — RUN A SESSION
----------------------------------------------------------------

  Two ways to drive the agent. They approve actions DIFFERENTLY —
  read the note below before choosing.

  (a) Command line — start a session against one target:

        python main.py run --target 192.168.163.131 \
                           --env env1 \
                           --mode human_in_loop

      IMPORTANT: started this way, human_in_loop prompts AT THE
      TERMINAL, not in the dashboard (main.py passes CLIGateway).
      You will see, for each proposed action:

        ────────────────────────────────────────────────────
        [Mode B] Proposed action for node 3f2a...
          Title:   Port scan target
          Tool:    nmap
          Params:  {"target": "192.168.163.131", ...}
          Why:     Establish attack surface before enumeration
        Approve? [y/N/skip]:

        y      execute it
        skip   skip this node and move on
        other  reject it

      Other CLI commands:

        python main.py list                  # past sessions
        python main.py tree <session_id>     # show the PTT

        # A session killed mid-run (Ctrl-C, VM power-off, SIGKILL)
        # cannot update its own row, so it stays 'running' for ever
        # and the dashboard keeps polling it. Sweep those:
        python main.py reconcile --dry-run   # show what is stuck
        python main.py reconcile             # mark them aborted
        python main.py reconcile --idle-minutes 60
        python main.py report <session_id>   # generate HTML report

        # add --pdf to also convert it. Needs one of weasyprint
        # (best fidelity), wkhtmltopdf, or headless chromium:
        #     sudo apt install -y weasyprint
        # Without one the HTML is still written and the command
        # prints what to install.
        python main.py report <session_id> --pdf

        # many hosts concurrently (CIDR, comma list, or host file)
        python main.py run-range --targets 10.10.0.0/24 \
                                --env env2 --workers 8

        # score a run against ground truth (FYP D5)
        python main.py benchmark \
            --manifest benchmark/ground_truth/metasploitable2.json

  (b) Web dashboard (best for demos and supervised training):

        uvicorn api.main:app --reload

      Then open http://localhost:8000 in your browser.

      Creating a session and running it are TWO separate actions:

        1. Fill in the new-session form (name, target, env, mode)
           and submit. This only creates the session row and
           bootstraps the 7 phase nodes — the agent is NOT running
           yet, and nothing has touched the target.
        2. In the session panel that appears, click "Start agent".
           That is what launches the agent loop (in a background
           thread). The button is disabled while a session runs.

      From the dashboard you can then:
        - watch the PTT update live
        - approve / reject the agent's proposed actions
        - abort a running session
        - save / download the generated report

      Sessions started HERE use DBPollingGateway: the node is set
      to awaiting_approval and the agent blocks until you click.
      That wait TIMES OUT AFTER 1 HOUR and auto-rejects the node,
      so don't leave a supervised session unattended.

  DO NOT MIX THE TWO. A session started from the CLI is blocked on
  a terminal input() prompt — it never writes awaiting_approval, so
  the dashboard will show nothing to approve and both sides hang.

----------------------------------------------------------------
 WHERE OUTPUT LANDS
----------------------------------------------------------------

  Paths are relative to the repo root, so run commands from there.

    artefacts/reports/<session_id>.html        pentest report
    artefacts/benchmarks/<session_id>.json     benchmark scores
    artefacts/benchmarks/<session_id>.md       benchmark summary

  The whole artefacts/ tree is gitignored — reports contain live
  vulnerability detail and credentials. Handle them per section 9
  of the FYP brief.

----------------------------------------------------------------
 OPERATION MODES
----------------------------------------------------------------

  autonomous       Agent executes every step it decides on, no
                   human gate. Use for benchmarks and unattended
                   runs.

  human_in_loop    Every action waits for your approval. WHERE it
                   waits depends on how you launched the session:

                     started from the CLI  -> CLIGateway
                         prompts in that terminal; blocks on
                         input() indefinitely.

                     started from dashboard -> DBPollingGateway
                         sets the node to awaiting_approval and
                         polls the DB; you click approve/reject
                         at http://localhost:8000. Times out
                         after 1 hour and auto-rejects.

                   Use for SOC training and demos.

----------------------------------------------------------------
 COMMON PROBLEMS
----------------------------------------------------------------

  - "docker: permission denied"
      You haven't re-logged-in since being added to the docker
      group. Run: newgrp docker

  - "Cannot connect to msfrpcd"
      Daemon not running. Re-check STEP 6.

  - "Target out of scope"
      The IP isn't covered by ALLOWED_TARGET_RANGES in .env.
      Add the CIDR, then RESTART THE PROCESS (see next entry).

      Two non-obvious causes:
        * You passed a HOSTNAME. Once an allowlist is set, only
          literal IPs pass the check — `--target myvm.lab` is
          always rejected. Use the IP. (URLs are fine; the host
          is extracted from them.)
        * You passed a CIDR as a tool target. Ranges fail the
          check by design, so the agent cannot widen a single-host
          run into a subnet sweep. Use `run-range` for that.

  - Edited .env but nothing changed
      Settings load once at process start. Stop the engine or
      the uvicorn dashboard completely and relaunch. Starting a
      new session in the same process re-uses the old values.

  - Dashboard shows nothing to approve
      You started the session from the CLI, so it is waiting on a
      terminal prompt, not the database. Answer it in that
      terminal, or restart the session from the dashboard. See
      STEP 8.

  - Session hangs, then "Approval timeout after 3600.0s"
      A dashboard session sat unapproved for an hour and the node
      was auto-rejected. Restart the session and stay with it.

  - Anthropic 401 errors
      ANTHROPIC_API_KEY in .env is wrong or empty.

  - "OPENROUTER_API_KEY is not set in .env"
      You set LLM_PROVIDER=openrouter without the matching key.

  - OpenRouter 401 / 402
      401 = bad key. 402 = out of credits; top up at openrouter.ai.

  - "LLM returned malformed JSON"
      The model wrapped its answer in prose instead of returning a
      bare JSON object. On OpenRouter, set OPENROUTER_JSON_MODE=true.
      If it persists, the model is a poor fit for the agent loop —
      switch back to LLM_PROVIDER=anthropic.

  - Benchmark cost column reads $0.00
      estimate_cost_usd() returns 0.0 for models missing from
      MODEL_PRICING in agent/llm.py. Add the model's per-1M input
      and output prices there.

  - Neo4j 'Unauthorized'
      NEO4J_PASSWORD in .env doesn't match the value baked into
      docker-compose.yml. Pick one and align both, then:
          docker compose down -v && docker compose up -d
      (The -v wipes the Neo4j volume so the new password sticks.)

  - "No module named ..."
      You're not inside the venv. Run: source .venv/bin/activate

  - CALDERA: "Connection refused" / caldera tool errors
      The server isn't running. Start it (STEP 6B) and leave it up.

  - CALDERA: 401 / 403 from the API
      CALDERA_API_KEY in .env doesn't match the server's red key.
      start_caldera.sh syncs them from .env — restart the server
      after editing .env so it rewrites caldera/conf/local.yml.
